# Assessment reporting

`GET /api/assessment/{year}/{area_code}` returns structured facts for `bucharest` or `sector_1` through `sector_6`. For 2025, `POST /api/reports/explore` turns them into a short project-screening diagnosis and conditional recommendations. Earlier years are historical reference points compared with 2025; they do not receive advice framed as if construction were happening in the past. `POST /api/comparisons` interprets sector comparisons or, for one sector across years, returns a five-observation timeline of LST and NDVI relative to the city mean in each year. A repeated relative signal in 2020, 2023, and 2025 is a planning flag, not a numeric forecast. The charts retain the detailed numbers; the reports are generated by `project_guidance.py`.

This checkout contains local LST and NDVI GeoTIFFs but no assessment SQLite/PostgreSQL database. `assessment.py` computes zonal LST/NDVI statistics from those rasters after basic CRS, nodata, and value-range checks. Independent source and temporal-processing validation is still needed. Land cover is a separate annual classified product from Esri / Impact Observatory / Microsoft, summarized from Sentinel-2 10 m GeoTIFF exports for 2018, 2020, 2023, and 2025 in `data/landcover-summary.json`. It is not derived from NDVI. The database can replace these source adapters later without changing the response shape.

The six-sector thermal and vegetation scores are *relative ranks*, using only the six sector means for the same year. They are project screening categories, not standardized physical or regulatory indices. Hotspot share uses the Bucharest-wide LST 90th percentile for the same year; the absolute threshold is returned with the percentage. This replaces the older 35 °C threshold, which classified nearly all valid pixels as hotspots in the tested 2023/2025 scenes. NDVI > 0.4 is reported only as a spectral threshold, never as classified land cover. Spearman and Pearson correlations use valid pixels on the same CRS and 30 m grid. The 2015/2020/2025 LST rasters have extra edge rows or columns after clipping; integer-cell shifts match their shared grid cells and exclude unmatched margins. No resampling or inferred pixels are used. The relationship describes spatial association, not a causal cooling estimate.

The API also returns `ndviSurfaceBreakdown` for each area/year, computed from valid local NDVI raster pixels in four mutually exclusive intervals: `<0`, `0–0.2`, `0.2–0.4`, and `≥0.4`. The frontend shows this as an NDVI surface-signal breakdown when real Land Cover is absent. It is deliberately not labelled as building, soil, water, tree, or park coverage.

The land-cover percentages are counts of classified pixels within the stored sector polygons; clouds and unknown codes are excluded. Built-up includes roads, and the results describe a city or sector, not an individual parcel. The report shows built-up share, but no validated composite resilience score. The annual land-cover product is distinct from the summer LST/NDVI data. The 2015 dashboard selection uses the closest available classification, 2017, and preserves that source year internally. For this prototype, summer rasters are treated as comparable inputs, but their temporal preparation has not been independently verified. Cross-year comparisons should be interpreted with that limitation. The supplied NDVI metadata currently describes a single August scene for each year, so a claim that the rasters are June–August composites needs source-method documentation.

The frontend's `MOCK_LAND_COVER` values remain hand-authored preview percentages used only in demo mode. The API mode serves the source-backed annual summary. Rebuild it with `backend/.venv/Scripts/python.exe backend/scripts/build_land_cover.py --download` from the repository root; source TIFFs remain ignored by Git. The derived JSON includes source, license, method, valid-pixel counts, and raster hashes.
