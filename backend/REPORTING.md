# Assessment reporting

`GET /api/assessment/{year}/{area_code}` returns structured facts for `bucharest` or `sector_1` through `sector_6`. `POST /api/reports/explore` renders the same facts as a deterministic report. The frontend displays the structured facts and the report sections.

This checkout contains local LST and NDVI GeoTIFFs but no assessment SQLite/PostgreSQL database and no validated Land Cover table or raster. The temporary source adapter in `assessment.py` computes zonal statistics directly from those GeoTIFFs after basic CRS, nodata, and value-range checks. Independent source and processing validation is still needed. The database can replace that adapter later without changing the response shape. Its records should supply validated dataset IDs, area/year statistics, Land Cover classes, relationship results, recommendation codes, and method versions described in `ASSESSMENT_DATA_CONTRACT.md`.

The six-sector thermal and vegetation scores are *relative ranks*, using only the six sector means for the same year. They are project screening categories, not standardized physical or regulatory indices. Hotspot share uses the Bucharest-wide LST 90th percentile for the same year; the absolute threshold is returned with the percentage. This replaces the older 35 °C threshold, which classified nearly all valid pixels as hotspots in the tested 2023/2025 scenes. NDVI > 0.4 is reported only as a spectral threshold, never as classified land cover. Spearman and Pearson correlations use valid pixels on the same CRS and 30 m grid. The 2015/2020/2025 LST rasters have extra edge rows or columns after clipping; integer-cell shifts match their shared grid cells and exclude unmatched margins. No resampling or inferred pixels are used. The relationship describes spatial association, not a causal cooling estimate.

The API also returns `ndviSurfaceBreakdown` for each area/year, computed from valid local NDVI raster pixels in four mutually exclusive intervals: `<0`, `0–0.2`, `0.2–0.4`, and `≥0.4`. The frontend shows this as an NDVI surface-signal breakdown when real Land Cover is absent. It is deliberately not labelled as building, soil, water, tree, or park coverage.

Until validated Land Cover is supplied, built-up pressure and resilience are explicitly unavailable. The report never uses the preview Land Cover percentages or sector offsets formerly embedded in the API. Cross-year comparisons show only metrics present on both sides and do not claim a long-term trend from individual summer scenes.

The frontend's `MOCK_LAND_COVER` values are hand-authored preview percentages. The backend branch currently visible in Git labels NDVI value ranges as buildings, trees, ground and water; that computation uses satellite NDVI, but no separate Land Cover classifier, class raster, accuracy assessment or source metadata is included. Those labels therefore cannot be treated as validated Land Cover percentages.
